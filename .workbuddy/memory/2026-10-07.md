## 「本地改了、线上不变」的真正根因：REFGROUPS 云端从不重建

现象：新增「油脂氧化指标」组（酸价 GB 5009.229-2025 / 过氧化值 GB 5009.227-2023）后，
本机 `prototype/data.js` 里该组 13 组 61 条齐全，**线上 data.js 与本机逐字节一致却是旧内容**，
`油脂氧化指标` 计数 0。

### 两个叠加原因

1. **`rebuild_repo.py` 故意不推 data.js**
   `KEEP_REMOTE = {".github/workflows/daily-check.yml", "prototype/data.js"}`
   ——设计原则是「只推代码，数据由 Actions 写」。这条规则本身是对的
   （本机 data.js 是旧的，推上去会污染），但它意味着**云端必须能自己重建 data.js**。

2. **云端管线漏了重建 REFGROUPS 的两步**（真正的缺陷）
   - `extract_data.py` 只在页面处于**内嵌形态**（`const X = [...]` 字面量）时才抽取常量；
     数据外置成 data.js 后页面是 `const REFGROUPS = (window.STDWATCH_DATA && …) || []`，
     `cut_literal()` 返回 None → 走 `_verify_only()` 分支，**只校验、绝不重写 REFGROUPS**。
   - 唯一会写 REFGROUPS 的是 `inject_refdata.py`（读 `data/_refjs.txt` 灌进 data.js 的
     `/* ---- REFGROUPS ---- */` 锚点），而它原先只在改引用组时由本机手动跑。
   - `daily_check.py` 里跑的是 `sync_std_to_proto.py`，它只改 **STD / LAWS / CATS** 三段，
     **不碰 REFGROUPS**。
   → 于是云端每天认真重建 data.js，却从不重建 REFGROUPS。该组只存在于本机文件里，永远上不了线。

### 修复
在 `daily_check.py` 的 `sync_std_to_proto.py` 之后补两步（都**不联网**，跑在 `if not skip:` 块外，
所以 `--skip-fetch` / 只部署模式也会执行）：
```python
run("重建通则引用组", ["scripts/build_refgroups.py"], allow_fail=True)
run("注入通则引用数据", ["scripts/inject_refdata.py"], allow_fail=True)
```
`build_refgroups.py` 读已入库的 `data/general_refs.json` 出 `_refjs.txt`（该 json 已在仓库里，176 KB）。

### 教训（同类问题的通用判据）
**改了 `prototype/data.js` 却发现线上没变时，先问「云端有谁能写这个字段？」**
本项目已踩过三次同一类坑，每次都是「本机改了、云端没有对应的重建步骤」：
- `fetch_wanted.py` 不在管线 → 点名标准从未生效
- `recategorize.py` 不在管线 → 生产标准显示 2 本（库里其实 5 本）
- `sync_std_to_proto.py` 不在管线 → 抓取结果进不了页面
- 本次：`build_refgroups/inject_refdata` 不在管线 → 通则引用组永远不更新
判据：**data.js 里每个字段都要能指出「云端哪个脚本负责写它」**；指不出来就是漏了。
