## 四、🔴 关键：源返回 0 条会覆盖历史快照（真 bug）

**现象**：2026-11-02 19:08 那次云端抓取，STD 从 341 掉到 293，
被「条数合理性检查」闸门拦下，没上线。

**根因**（`scripts/crawler.py` 抓取主循环）：
```python
if not stds and not load_snapshot(code):
    raise RuntimeError(...)      # 只有「空 + 无历史」才报错
new = {...}                     # 空结果 → new = {}
save_snapshot(code, new)        # ← 把 54 条的历史覆盖成 0 条！
```
SRC-08 团标站当天临时返回 0 条（上次 54 条），assoc 分类 61→11。

**修法**：空结果 + **有历史** → 沿用旧快照、记警告、不产生「批量下架」事件；
空结果 + 无历史 → 仍判未接通（保持原语义）。

**新增回归**：`scripts/test_snapshot_guard.py`（9 条断言，三种情形全覆盖）。

**教训**：官方站点接口抽风是常态，不是异常。**「源变空」必须先怀疑自己，再怀疑数据。**

## 五、🔴 关键：推送必须用增量，不能用 rebuild_repo.py

`rebuild_repo.py` 每次把本地**全部**文件逐个 POST /git/blobs 重传：
- 本地 1156 个文件里有 785 个在 `.workbuddy/tmp`（4 份 13 MB baseline 快照 + 探针文件），
  一次就是 **50 MB 垃圾**
- 网络一慢 **20+ 分钟**，而且每次白传没变的东西

**新增 `scripts/push_incremental.py`**：
- GET 远端 tree（1 次）→ 本地算 git blob sha = `sha1("blob <size>\0" + 内容)`
- sha 相同就跳过，只传变了的
- 实测：116 个变更 → **3 分钟**；5 个变更 → **29 秒**

**同步修**：
- `rebuild_repo.py` 的 `collect()` 排除 `.workbuddy/tmp`
- `deploy.py` 的 `changed_files()` 排除 `.workbuddy/tmp`（否则每次都被判成 full）
- `deploy.py` 的推送步骤改调 `push_incremental.py`
